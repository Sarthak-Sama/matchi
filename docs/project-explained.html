Internal field guide · September 2026

Matchi, from first principle to ranked result.

Matchi helps someone choose a Tokyo area to live in. It starts with a real-life question—“where can I live if I need to get there, can spend this much, and care about these things?”—then makes its answer explainable instead of magical.

One sentenceWe combine public geographic data, a deliberately approximate rail model, and transparent scoring to rank Tokyo localities by fit.

01 · The product

An area-fit guide, not a property search site.

A user picks a workplace or other destination, an arrival time, maximum commute, monthly budget, home layout, and one to five lifestyle priorities. Matchi returns up to 20 ranked localities, showing their estimated rent, commute, nearby stations, preference evidence, and trade-offs.

The promise is not “we know the perfect apartment.” It is: we narrow a huge city into areas worth exploring, and show why each made the cut.

Words that matter

Modeled area rent is a statistical estimate for an area and layout—not a live listing.

Typical weekday estimate is a network model—not a live timetable or route guarantee.

Quietness is a proxy based on land use, road/rail exposure, and nightlife—not a noise measurement.
02 · The decisions we made

Prove the engine, then make it real.

  1. Aug 22: lean vertical slice

    The first commits created a TypeScript monorepo, PostGIS schema, shared contracts, Fastify API, a seeded sample of about 20 stations, rent estimation, Dijkstra routing, scoring, and focused tests. That proved a complete product loop before heavy data work.

  2. Aug 23–25: real data pipeline

    Explicit MLIT, e-Stat/REINS, OpenStreetMap, and transit imports replaced the seed-only idea. The work added import audit records, source validation, English landmark search, guards against destructive test runs, and fixes for real-world geometry.

  3. Aug 24: richer everyday-life choices

    Five axes joined the original set through one shared registry: konbini, cuisine variety, parks, late-night food, and everyday health. A single registry stops UI labels, database columns, and scoring from drifting apart.

  4. Aug 31: locality pivot

    The original recommendation was an 800 m station circle. The current unit is a named e-Stat town/chōme locality. Nine deterministic sample points inside each locality, each linked to nearby stations, represent the locality rather than a single station pin.

  5. Aug 31–Sep 1: production polish

    The UI became an editorial field guide, with a landing page and dedicated /find search. The database moved to Neon; stale autocomplete/search responses were prevented from repainting the page.

Old model: “Which station area should I live near?”

Current model: “Which named locality fits my life, given representative places inside it and their access to rail?”

Legacy station-area tables remain useful support data. But the live optimizer reads localities and locality_metrics.
Why not a huge platform?
The spec intentionally deferred Redis, queues, accounts, snapshot versioning, timetable routing, generated clients, and enterprise monitoring. The early goal was a credible, auditable answer with the fewest moving pieces.

Web

Next.js provides the public interface. / tells the product story; /find is the accessible form and ranked results. Small handwritten fetch helpers and request-generation checks keep it easy to follow.

API

Fastify is the thin decision layer: validate JSON, read candidates, run the rail algorithm in memory, filter, score, and return evidence. Helmet, CORS, request IDs, rate limits, structured errors, and graceful shutdown harden it.

Shared

Contracts, layout sizes, scoring weights, lifestyle registry, confidence terms, and rent math live once. Frontend and backend import the same definitions.

Scripts

Scripts are explicit rather than a generic ETL framework. Each source has a clear import command; derive precomputes product-ready metrics.

Database

PostgreSQL stores relationships; PostGIS answers geographic questions such as within-distance and polygon overlap. It is the durable system of record.

Transit graph

The API loads rail_edges into peak/off-peak in-memory graphs at startup. The DB remains authoritative, but a user search does not need a large graph query.

The core question is geographic. PostGIS stores actual shapes and computes meter-based proximity and overlap. This is more faithful and safer than app-side coordinate approximations.
05 · One search, end to end

What happens after “Find my Matchi.”

  1. Validate

    The request includes exactly one destination (station or point), arrival time, budget, layout, commute cap, and 1–5 rated priorities. Shared Zod schemas reject malformed or ambiguous input.

  2. Resolve destination

    A station is a graph seed. A point finds usable stations within 1.5 km and includes the walk to that point, so offices and landmarks work too.

  3. Run reverse Dijkstra once

    The API chooses peak or off-peak graph from arrival time, starts at the destination, and searches backward. One run gives best rail cost from every station to the same destination.

  4. Build locality commute

    For each of nine samples, it tries nearby stations and also a direct walk if appropriate. The median sample is the headline; the 25th–75th percentile becomes the displayed range.

  5. Recalculate rent

    Stored rent inputs are recomputed for the user’s actual layout rather than assuming one layout fits everyone.

  6. Filter, score, explain

    Disconnected, over-commute, and over-budget places are excluded. The rest score, receive evidence and reasons, then sort by score, commute, rent, and stable ID. Top 20 return.

Why reverse Dijkstra?

Matchi has many possible origins and one destination. Normal routing solves one origin → one destination; reversing solves destination → every origin in one pass.

What is counted
Ride time + expected wait when boarding a line + 5-minute transfer penalties + access walk + destination walk.

Period is not a timetable
07:30–10:00 uses peak weights. It is not a scheduled, departure-specific trip plan.
06 · Recommendation engine, in plain language

Think of it as a very transparent elimination tournament.

The engine does not begin by guessing the “best” area. It first makes a complete candidate card for every locality with usable data. Then it removes localities that cannot meet the user’s non-negotiables. Only after that does it compare the survivors. This order matters: a lovely but over-budget or too-far-away place should not win because it has excellent cafés.

1. Build a candidate card

For every locality, the API loads its boundary, centre point, nine representative samples, each sample’s closest stations, saved rent inputs, and normalized lifestyle measurements. It will not create a candidate if crucial information is missing—for example, no ward assignment, no rent statistic, or incomplete normalized lifestyle data. That is a “fail closed” decision: no made-up score is better than a misleading score.

2. Work out its commute

First, the destination becomes one or more rail-network starting points. If the destination is a station, that is simple. If it is a landmark or map point, the API finds stations within 1.5 km and treats the destination-side walk as part of the journey.

Next it selects the peak or off-peak graph from the requested arrival time and runs reverse Dijkstra once. “Reverse” means it starts at the destination and expands outward. Imagine pouring paint from the destination through every rail line: the first time paint reaches a station, it has found the fastest known way from that station back to the destination.

For each locality sample, the engine tries the sample’s up-to-three nearby stations. It adds the sample-to-station walk to the rail estimate and keeps the quickest option; it also considers walking all the way to the destination, which can beat rail for close destinations. Of the usable sample journeys, the middle one becomes the locality’s main commute. The middle 50% becomes its displayed range, which admits that one edge of a locality can be easier to reach from than another.

3. Recalculate rent for this person

The database keeps the underlying rent ingredients, not a fixed answer. The engine uses the selected layout’s minimum, midpoint, and maximum sizes with ward rent-per-square-metre, management fee, and the locality’s land-price adjustment. It returns a low / median / high modeled range. The median is used for the budget decision.

4. Apply the hard filters

There are three gates, in this exact order:

DisconnectedNo usable walk or rail path → exclude.
CommuteTotal estimated time exceeds the person’s maximum → exclude.
BudgetMedian modeled rent exceeds the monthly budget → exclude.

If nothing survives, Matchi does not pretend to have recommendations. It counts which gate excluded the most localities and suggests a concrete relaxation, such as a higher budget or commute cap based on the lower quartile of excluded values.

5. Score survivors and make reasons

The survivors receive affordability, commute, and selected-lifestyle scores. The engine turns each into visible point contributions, rounds them consistently, and sums them. It makes short “strength” and “weakness” statements from notably high or low factor scores, prioritizing factors the user weighted most.

How the rail path itself is priced

Ride edge

Moving between adjacent stations adds typical rail time. When boarding a new line, the engine also adds expected wait time. Staying on the same line does not charge another wait.

Transfer edge

An explicit interchange adds its travel time and a five-minute transfer penalty. Changing lines implicitly also adds that five-minute penalty. The lowest confidence on a route becomes the route confidence.

Path reconstruction

Dijkstra remembers the exact state it used—station and current line—rather than only the station. This avoids incorrectly reconstructing a route when reaching the same station on different lines produces different future costs.

An important separation: filtering answers “is this possible for this person?”; scoring answers “among the possible options, which trade-off fits best?” This is why a high lifestyle score cannot smuggle an unaffordable locality into the results.
07 · Scoring

Simple enough to repeat out loud.

overall score = 30% affordability + 30% commute + 40% lifestyle Lifestyle’s 40% is divided only among selected priorities: low = 1 · medium = 2 · high = 4 · essential = 8 “Essential” is a strong ranking weight, not a hidden hard filter.

Affordability · 30%

Rent at or below 80% of budget scores 100. It declines linearly to 0 at the budget cap. Over-budget localities are already filtered out.

Commute · 30%

15 minutes or less scores 100. It declines linearly to 0 at the user’s cap. Over-cap localities are already filtered out.

Lifestyle · 40%

Every selected axis has a 0–100 locality score. User importance determines how the 40% is split.

Rent: explainable on purpose

modeled rent = ward rent per m² × chosen layout size × local land-price multiplier + ward management fee low: minimum layout size × 0.90 median: layout midpoint high: maximum layout size × 1.10

The multiplier compares local residential land prices to the ward median, uses a gentle fourth-root adjustment, and clamps to 0.85–1.15. Fewer than three points (or unusable data) falls back to 1.0 and lowers confidence.

Lifestyle: what is actually measured

SupermarketsRestaurantsQuietness proxyKonbiniCuisine varietyParks & green spaceLate-night food (approx.)Everyday health

For each sample point, Matchi counts POIs within 800 m and calculates road/rail, residential-zoning, and green-space shares. It takes medians across the nine samples. Diminishing-return logarithmic normalization prevents “more of the same” from dominating. Quietness is 50% residential zoning, 30% inverse road/rail exposure, and 20% inverse nightlife density.

Explainability is a product feature: every factor includes raw value, component score, effective weight, point contribution, source date, confidence, direction, and plain-English explanation. Reasons for/against use strong scores above 66% or below 34%, ordered by importance.
07 · Operating it

Refreshes are manual and controlled.

The normal live-data sequence is data:prepare → data:refresh --source all → data:validate. It imports approved data, rebuilds transit topology, derives metrics, validates results, and reminds the operator to restart the API so it reloads rail edges.

Archives and generated GeoJSON live in gitignored data/. PostGIS is the system of record. The data catalog requires actual SHA-256 values, and every import creates an import_runs audit row.

Why Neon and direct connections?
The project moved to Neon. The long-running API uses a bounded direct pool—not PgBouncer—because session state such as search_path can leak between pooled clients after restores. TLS verification is enforced in shared code.
08 · Honest boundaries

Credible because it keeps its limits visible.

No live listings

Public ward rent statistics, lightly calibrated with land prices, cannot know a building’s age, floor, availability, or deal terms.

No live journey planner

The graph is compact and typical. It does not retain full timetable trips/calendars or use RAPTOR/OpenTripPlanner.

No flood score

Flood appeared in the historical spec, but migration 0009_remove_flood removed its data and score. It is not an active feature.

No exact walking routes

Access is distance-based with a detour factor. The 800 m amenity lens is not a pedestrian isochrone.

No fabricated incomplete data

Missing rent or normalized lifestyle metrics exclude a candidate; the API does not invent scores.

No premature infrastructure

Redis, queues, accounts, snapshots, advanced alerting, and scheduled imports wait for evidence that they are needed.

Future candidates: line diversity/direct reach, quiet↔lively preferences, duplicate-area handling, hilliness, congestion, land-price trends, earthquake/liquefaction risk, last trains, and real walking isochrones.
